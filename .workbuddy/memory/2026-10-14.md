## zip 有声书：解析慢 + 排序乱（两个 bug 一起修）

用户反馈：添加 `dir/dir/*.zip` 的有声书要解析好几分钟；列表不是自然排序（第一卷之后直接跳到第七卷）。

### 排序根因
- `ChapterId.compareTo` → `NaturalOrderComparator.uriComparator`：`pathSegments` 是**百分号编码**的，中文被编码成 `%E7%AC%AC...`，中文按 UTF-8 字节序比较 → 一(4E00) < 七(4E03) < 二(4E08) ... 所以出现「第一卷 → 第七卷」
- `NaturalComparator` 只认 ASCII 数字，不认中文数字

### 排序修复
- `core/common/.../NaturalComparator.kt`：新增 `readNumber/readDecimalNumber/readChineseNumber`，在「不是双方都是 ASCII 数字」的分支里做数值比较；中文数字支持 零〇一壹二两贰…九玖 / 十百千（拾佰仟）/ 万亿（萬億），如 十五=15、一百二十三=123、一万二千=12000
- `core/common/.../NaturalOrderComparator.kt`：`comparableSegments()` 对每个 path segment 做 `Uri.decode`（zip:// 的第一段是归档 uri，解码后**不**再按 "/" 拆），decode 失败回落原串
- `core/common` 测试补了中文数字 / 中英混排 / zip uri 三组用例

### 性能根因
`MediaAnalyzer.analyze` 对 zip 内音频调用 `readEntryBytes` → **整个文件解压进 ByteArray**，几百个文件 × 数十 MB = 数分钟；且 `ZipArchiveProvider` 的 `evict()` 是 suspend 却在 `mutex.withLock` 里调用（锁重入风险），MAX_OPEN_ARCHIVES=3 太小。

### 性能修复
- 新增 `core/zip/ZipEntryDataSource.kt`：可 seek 的流式 DataSource（open 时重开流 + skip 到 position，长度取 `header.uncompressedSize`；长度未知时退回整体缓冲）。core/zip 新增 `media3-datasource` 依赖（libs.versions.toml 加 `media3-datasource`）
- `ZipArchiveProvider`：新增 `withEntryDataSource(uri) { factory -> }`，归档在 block 期间**引用计数锁定**不会被关闭；`withArchive` 取代原 `open`；`evict()` 改为非 suspend（原来在 withLock 内调用），`MAX_OPEN_ARCHIVES` 3→8；`ZipArchive.openStream` 加 `synchronized(zipFile)`（zip4j 的 `openInputStreams` 是普通 ArrayList）
- `MediaAnalyzer`：zip 走流式，失败（或 duration/metadata 取不到）才退回整体读入；mka/mkv 仍整体读入（matroska 需随机访问）；`mediaSourceFor` 每次新建（并发安全）；取消异常不吞
- `ChapterParser`：先顺序收集音频文件，再用 `Dispatchers.IO.limitedParallelism(4)` 并发解析（原来完全串行）
- `MediaScanner`：去掉 `sortedBy { it.audioFileCount() }`（每个 book 全树 walk 一次），改按名字自然排序
- `ChapterRepoImpl.cache` 改 `ConcurrentHashMap` + `Holder`（并发解析需要；CHM 不能存 null）
- 顺手修了 scanner 测试模块**既有的编译错误**（zip 提交后 `ChapterParser`/`BookParser`/`MediaAnalyzer` 构造参数没同步更新）；`MediaScannerTest.analyzeCalls` 改 `AtomicInteger`（并发计数）

## HiFi 模式设置开关（float output）

用户需求「支持一下hifi」→ 确认为在设置页加「HiFi 模式」开关，开启时走高精度直出链路。

实现（media3 1.10.1，核心 API：`DefaultRenderersFactory.setEnableAudioFloatOutput(true)`）：

- `core/data/api` StoreQualifiers.kt：新增 `HiFiModeStore` qualifier
- `core/data/impl` StoreModule.kt：新增 `DataStore<Boolean>` provider（fileName "hiFiMode"，默认 false）
- `core/playback` OnlyAudioRenderersFactory.kt：构造时 `runBlocking` 读开关并 `setEnableAudioFloatOutput(...)`
- `features/settings`：SettingsViewState/SettingsListener/SettingsViewModel/Settings.kt 加开关行（AudioFile 图标 + Switch）
- 字符串：`settings.playback.hifi_mode.title/summary`，values + values-zh-rCN
- SettingsViewModelTest：补 hiFiModeStore 参数和 toggle 测试（未运行，按用户规则）

关键事实（已通过反编译 media3 1.10.1 AAR + 官方 javadoc 验证）：
- float 输出仅对高解析 PCM（int24/int32）源生效（`shouldUseFloatOutput` = enableFloatOutput && isEncodingHighResolutionPcm），16bit 音源行为不变
- float 模式下 DefaultAudioProcessorChain 被替换为 ToFloatPcmAudioProcessor：跳过静音（SilenceSkipping）失效；变速自动改走 AudioTrack.setPlaybackParams（无需额外开关，`shouldApplyAudioProcessorPlaybackParameters` 逻辑保证）
- 开关在播放器创建时读取（PlaybackService.onCreate → PlaybackGraph），运行中切换需重启应用生效，摘要文案已如实说明
- 与既有的 media3_audio_offload feature flag 相互独立，未做耦合
