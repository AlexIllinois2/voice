## 快扫 + 后台回填时长（用户第三轮需求）

用户需求：「第一次解析不要一个一个解压详细解析 直接获取内容列表 然后快速出有声书 有个列表就行 时常这些后台慢慢解析出多少回填多少就行 性能优先 能分批处理就分批处理」。

### 设计：快 phase + 慢 phase
- **快 phase**（扫描时）：`ChapterParser.parse()` → `listChapters(documentFile, onProgress)`：只收集音频文件列表，章节 duration=0、name=文件名，`getOrPut` 复用未变章节（已解析过的时长不丢）；不再调 MediaAnalyzer。`BookParser.parseAndStore(chapters, file)` 直接建书入库（analyzed=null，书名先用 `bookDisplayName()` 占位）
- **慢 phase**（扫描后）：新增 `ChapterEnricher`，收集所有 duration<=0 的章节 → `interleave` 跨书轮询（每本书的先出，避免只解析第一本）→ `chunked(8)` + `limitedParallelism(4)` 分批并发分析 → 每章完成 `put` 回填（name/duration/markData），逐章上报 `ScanProgress(phase=Enriching)`；首章元数据交给 `BookParser.fillMetadata` 回填书名/作者等
- `MediaScanTrigger`：scan（快）→ `bookRepo.all()` → `chapterEnricher.enrich(books)` → coverScanner.scan(books)；`scannerActive` 在回填期间保持 true；`scanProgress` 回填期显示「正在解析时长 x/y · 章节名」
- 防改名覆盖：`fillMetadata` 仅当 `content.name == bookFile.bookDisplayName()`（占位名）才回填
- 播放自愈：`DurationInconsistenciesUpdater`（既有）在播放时用 player.duration 纠正；enricher 里 `chapterRepo.get` 重读 + duration>0 跳过，避免覆盖播放器已修好的值
- 回填可见性：`ChapterRepoImpl.updates`（put 时递增的 sampled StateFlow）→ `BookRepositoryImpl.flow()/flow(id)` 用 combine 重新 map（每秒最多一次）；`sample` 会延迟首次发射，故用 `.onStart { emit(0L) }` 保证列表立即出现
- `MediaScanner` 里 currentChapterGone / isActive 修正逻辑保留（曾误删，singleFileDeletion 等测试依赖）
- `bookDisplayName()` 提取为 `BookDisplayName.kt` 顶层 internal 函数（MediaScanner/BookParser 共用），替代原 BookParser 私有 `bookName()`

## 回填失效 + 无限循环 bug 修复 + 通知栏进度（用户第四轮反馈）

用户反馈：「解析好几次了解析完都没有起作用 / 进入其他界面再回主界面又会自动重新解析时长 不停循环 / 解析时长应并行独立，不影响管理和播放其他有声书 / 可在通知栏显示解析进度」

### 根因（推断 + 修复）
- **同一个 zip 的多个条目并发读会读坏数据**：`ZipArchive.openStream` 只用 `synchronized(zipFile)` 保护了流的**创建**，但 zip4j 的所有流共享同一个 RandomAccessFile，4 路并发读时文件指针互踩 → media3 取不到时长 → `analyze` 返回 null → chapter 永久 duration=0 → 每次扫描重新回填 = 无限循环（10-14 引入流式 DataSource 后一直存在、当时未实机验证的隐患）
- 修复：`ZipArchive` 加 `readLock: Mutex` + `suspend fun <T> withEntryRead(block)`；`ZipArchiveProvider.withEntryDataSource` 与 `readEntryBytes` 都包在锁里。**跨书并行保留，同一本书内串行**
- **失败重试上限**（防御性）：`ChapterEnricher.failedAttempts`（CHM<ChapterId,Int>），失败 3 次后跳过；`resetFailures()` 在 `scan(restartIfScanning=true)` 时清空；新增 `pendingCount(books)`；`enrichChapter` 改返回 Boolean

### 结构解耦（并行独立）
- `MediaScanTrigger` 拆成两个 job：`scanningJob`（列文件，`scannerActive`）与 `enrichJob`（回填，`enrichActive`）。enrichJob 用 `scope.launch` 启动（**不是** scanningJob 的子 job），所以新扫描不会取消它；enrich 期间 `scannerActive=false`，书架/播放不被阻塞
- 只有 `pendingCount > 0` 才启动 enrich；扫描结束无待办则立即清进度
- VM：`isLoading = scannerActive || enrichActive`

### 通知栏进度
- 新增 `core/scanner/ScanProgressReporter`（report/dismiss），`MediaScanTrigger` 只在**回填阶段**上报
- `:app`：`ScanProgressReporterImpl`（@ContributesBinding(AppScope)，ContextCompat.startForegroundService + notify；后台启动被拒时降级为普通通知）、`ScanService`（foregroundServiceType=dataSync，只持通知不干活）、`ScanNotification`（channel scan_progress，进度条 + 点击回 App）

## 修复 zip 内 m4a/mp4/matroska 时长解析（用户问「zip 里的 m4a」）

用户问「zip 里的 m4a 时长解析支持了？」。发现工作区里有一段没提交完的手改（MediaAnalyzer.kt），意图是给 zip 条目加「随机访问格式整体缓存再解析」分支（m4a 的 moov 在文件尾，流式解压每次 seek 都要重新 inflate，必须整体读内存），但**编译不过**，两个问题：

1. `RANDOM_ACCESS_EXTENSIONS` 常量全仓库未定义 → 修复：MediaAnalyzer 加 `private companion object { val RANDOM_ACCESS_EXTENSIONS = setOf("mp4","m4a","m4b","mka","mkv") }`
2. 手改把主函数 `analyzeWith` 误改名成 `logOrRethrow`（与既有重载撞名）且丢了 `suspend` → 恢复为 `private suspend fun analyzeWith(...)`

链路：ChapterEnricher.enrichChapter → MediaAnalyzer.analyze(zip entry) → m4a 等命中 RANDOM_ACCESS_EXTENSIONS → `readEntryBytes`（archive.withEntryRead 串行锁内整体读内存）→ ByteArrayDataSource → media3 MetadataRetriever 读 moov 拿 duration；mp4 章节走 `parseMp4Chapters` 用同一个 ByteArrayDataSource factory。mp3 等仍走流式 ZipEntryDataSource，失败兜底整体读。注意整个 entry 进内存，超大 m4a 章节有内存峰值，是该设计的既定权衡。

## scanner 单测结清（ADTS 修复后的验证轮）

## zip 自动解析闸门从「会话级内存」改为「持久化」（用户第九轮：纠偏两次）

- 用户纠偏：① 「每会话一次」不对——**成功后应永久不再自动解析，zip 是不可变的**；② 打断补充「**失败也一样永久不再自动解析**」。即：一个 zip 在其生命周期内最多被自动解析一次（成败皆然），必须落盘且不能靠会话内内存
- 分工：**成功**天然由 `chapter.duration > 0` 持久化满足；**失败**（duration 恒 0）必须有独立持久状态，否则每次进程重启又满足 Auto 条件 → 反复弹通知
- 存储选型：**DataStore<Set<String>> 而非 Room 新表**——量小（zip 数量级）、语义是「一次性开关集合」、免 59→60 AutoMigration 风险，符合本仓 Map/Set 类偏好在 DataStore 的既有惯例（如 FeatureFlagOverrides）
- 新增：
  - `core/data/api/.../repo/ZipParseAttemptRepo.kt`：`attemptedZips(): Set<String>` / `markAttempted(zipUris: Collection<String>)`
  - `core/data/impl/.../repo/ZipParseAttemptRepoImpl.kt`：`@SingleIn(AppScope) @ContributesBinding(AppScope)`，`DataStore.updateData { it + zipUris }`，读写各自 catch IOException → 读失败按空集（宁可再解析一次也不阻断扫描）、写失败只告警；`markAttempted` 空集合直接 return
  - `@ZipParseAttemptStore` 限定注解 + StoreModule 提供者 `factory.create(SetSerializer(String.serializer()), emptySet(), "zipParseAttempts")`
- `ChapterEnricher`：删掉 `autoParsedZips: MutableSet`（ConcurrentHashMap.newKeySet 随进程消失）；注入 repo；`pendingCount`/`chaptersToParse` 改 **suspend**（DataStore 读取）；Auto 模式在**解析前**批量 `markAttempted`（进程中途被杀也不会重来）；`resetFailures()` 只清 in-memory 失败的 `failedAttempts`，**不再清 zip 闸门**（`scan(restartIfScanning=true)` 仅删书后调用，不应重开闸）
- 测试（scanner 65 全绿 + data:impl 新增 2 个）：`ChapterEnricherTest` 植入内存 fake repo 模拟持久化，`newEnricher()` helper 造「重启后的新 enricher」→ 用例 `a zip that failed to parse is not parsed again after a restart`（新实例 pendingCount=0、不调用 analyze，仅 Mode.Retry 才再解析）、`resetFailures keeps the zips that were parsed automatically`（旧的 `resetFailures allows parsing a zip automatically again` 语义反转后删除）；`ZipParseAttemptRepoTest` 用既有 `MemoryDataStore<T>`（test helper）验证累积/跨实例读取/空集合不写入

## 回主页仍闪一下「正在解析」——其实是扫描进度（用户第十轮）
